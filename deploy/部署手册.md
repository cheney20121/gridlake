# Gridlake 私有化部署手册

Gridlake 由两部分组成，打在同一个安装包 / 镜像里，**运行时只有一个进程**：

| 组成 | 说明 |
|---|---|
| 表格服务 `gridlake` | Rust + 内置 DuckDB，千万行数据的存储、筛选、透视、公式下推、工作簿保存 |
| 前端页面 `web/` | 由表格服务直接提供（`LEDGER_WEB_DIR`），浏览器访问 `http://服务器:8787/excel` |

登录方式由 `LEDGER_AUTH_MODE` 决定：内置账号（推荐）、对接已有的登录网关、由反向代理传入身份，或不登录（仅限内网试用）。见「登录与权限」。

## 一、服务器要求

| 数据规模 | CPU | 内存 | 磁盘（数据 + 7 份备份） |
|---|---|---|---|
| ≤ 100 万行 | 2 核 | 4 GB | 10 GB |
| 1000 万行 | 4~8 核 | 8 GB 起，16 GB 更从容（上限不必手动设，默认取内存的 30%） | 1000 万行约 1.4 GB/份 → 建议 ≥ 30 GB SSD |
| 5000 万行 | 8~16 核 | 16 GB+ | 约 1.2 GB/千万行/份（随列数与重复度变化）→ ≥ 100 GB SSD |
| 1 亿行 | 8 核+ | **16 GB 起**（8 核 16 GB 实测：筛选 / 透视 / 公式 / SQL 秒级到十几秒，见平台需求文档「亿级规模实测」） | 实测 8 列 1 亿行库文件 2.4 GB / 份 → ≥ 60 GB SSD |

- 系统：Linux x86_64 / aarch64（如 CentOS / Ubuntu / 麒麟 / 统信 UOS），或任意能运行 Docker 的环境
- 安装包里的程序动态链接系统 glibc，**要求服务器的 glibc 版本不低于打包机**（`ldd --version` 查看）：面向 CentOS 7/8、麒麟 V10 等较老系统时，在同版本系统上执行 `deploy/package.sh` 打包
- 必须使用本地磁盘（SSD 优先），**不要放在 NFS 等网络文件系统上**（数据库文件锁与随机读写性能无法保证）
- 浏览器：Chrome / Edge 100+

参考性能（1000 万行，8 核）：按条件筛选 0.5 s，滚动取数 10~20 ms，透视 0.1~0.2 s，全量备份 10 s。

## 二、安装

### 方式 A：安装包 + systemd（推荐）

```bash
tar -xzf gridlake-0.1.0-linux-x86_64.tar.gz
cd gridlake-0.1.0-linux-x86_64
sudo ./install.sh
```

安装后的目录：

| 路径 | 内容 |
|---|---|
| `/opt/gridlake/bin/gridlake` | 程序 |
| `/opt/gridlake/web/` | 前端页面；`config/index.js` 为运行时配置 |
| `/etc/gridlake/ledger.env` | 服务配置（见第三节） |
| `/var/lib/gridlake/ledger.duckdb` | **全部业务数据**（数据集、工作簿、版本、月结记录） |
| `/var/lib/gridlake/backups/` | 自动备份 |
| `/var/lib/gridlake/tmp/` | 临时文件（上传暂存、查询游标、内存不足时的落盘），可随时清空 |

常用命令：

```bash
systemctl status gridlake          # 状态
systemctl restart gridlake         # 修改配置后重启
journalctl -u gridlake -f          # 日志
```

### 方式 B：Docker

```bash
mkdir -p data && chown -R 10001:10001 data

# 使用发布的镜像（版本见 GitHub Releases）：
docker compose -f deploy/docker-compose.yml up -d

# 或者自己构建（在仓库根目录；内网可加 --build-arg NPM_REGISTRY=... 指定依赖源）：
docker build -f deploy/Dockerfile -t gridlake:local .
GRIDLAKE_IMAGE=gridlake:local docker compose -f deploy/docker-compose.yml up -d
```

compose 文件默认开启内置账号登录（`LEDGER_AUTH_MODE=local`）。镜像默认监听 `0.0.0.0`，所以直接 `docker run` 时必须自己设置 `LEDGER_AUTH_MODE`，否则服务会拒绝启动。

数据在 `./data`。容器内执行运维命令：`docker exec gridlake curl -s http://127.0.0.1:8787/api/admin/status`。

## 三、配置

### 服务配置 `/etc/gridlake/ledger.env`

| 变量 | 默认值 | 说明 |
|---|---|---|
| `LEDGER_ADDR` | `127.0.0.1:8787` | 监听地址；对外服务用 `0.0.0.0:8787` |
| `LEDGER_DB` | `data/ledger.duckdb` | 数据文件 |
| `LEDGER_WEB_DIR` | 不启用 | 前端页面目录（含 `index.html`） |
| `LEDGER_MEMORY_LIMIT` | **机器（或容器）内存的 30%**，不少于 1GB，启动日志里会写明 | 如 `8GB`；`off` 改用 DuckDB 自己的默认（内存的 80%）。**这只约束 DuckDB 的缓冲区，不是进程内存的硬上限**：排序游标已能遵守上限（1 亿行排序在 1GB 限制下也能建），但**精确**分位数（中位数 / P95）聚合要把整列数值放在内存里，实测 1 亿行上 4 个并发即使限制 1GB 也会到 3GB 以上（改用透视里的「近似中位数 / 近似 P95」峰值只有 0.8GB），所以默认值取得保守；想要硬上限请用下面的 systemd `MemoryMax` / Docker `mem_limit` 兜底 |
| `LEDGER_HEAVY_QUERIES` | 按内存上限算：每 2GB 一个，1~4 个（16GB 机器为 2） | 同时进行的「大计算」（透视、SQL、异常发现、带筛选 / 排序的游标）个数，超出的排队；整表浏览、取行、公式汇总等轻量请求不排队 |
| `LEDGER_HEAVY_WAIT_SECS` | `120` | 大计算排队的最长等待秒数，超过返回「服务繁忙」（503）；排队中的请求若浏览器已断开会自动退出队列 |
| `LEDGER_THREADS` | CPU 核数 | 与其他业务共用服务器时调小 |
| `LEDGER_BACKUP_AT` | `02:30` | 每天自动备份时间；`off` 关闭 |
| `LEDGER_BACKUP_KEEP` | `7` | 保留最近几份备份 |
| `LEDGER_BACKUP_S3_BUCKET` | 空 | 设置后，每次备份完成会再上传到这个对象存储桶（S3 协议），见「备份与恢复」。同时必须设置下面两个密钥变量 |
| `LEDGER_BACKUP_S3_ACCESS_KEY` / `LEDGER_BACKUP_S3_SECRET_KEY` | 空 | 上传用的访问密钥（建议单独建只管这个桶的密钥） |
| `LEDGER_BACKUP_S3_ENDPOINT` | 空（AWS S3） | 自建 / 其他云的服务地址，如 `https://minio.corp:9000`，只写主机和端口 |
| `LEDGER_BACKUP_S3_REGION` | `us-east-1` | 区域 |
| `LEDGER_BACKUP_S3_PREFIX` | `gridlake-backups/` | 对象键前缀 |
| `LEDGER_BACKUP_S3_PATH_STYLE` | 自动 | `1` 路径风格 / `0` 虚拟主机风格；不设置时填了服务地址用路径风格，AWS 用虚拟主机风格（规则同数据连接） |
| `LEDGER_BACKUP_S3_KEEP` | `30` | 对象存储上保留最近几份 |
| `LEDGER_BACKUP_S3_VERIFY` | 空 | `download`：每次上传后把备份下载回来做恢复演练（多一次下载流量；默认只核对大小） |
| `LEDGER_BACKUP_S3_PART_MB` | `64` | 分片上传的分片大小（MB，1 ~ 5000）；超过一片的备份才会分片，一般不用改 |
| `LEDGER_BACKUP_DIR` | 数据目录下 `backups/` | 建议放在另一块磁盘（同时加入 `gridlake.service` 的 `ReadWritePaths`） |
| `LEDGER_MAX_UPLOAD_MB` | `1024` | 单个上传文件上限 |
| `LEDGER_ADMIN_TOKEN` | 不设置 | 运维接口令牌；不设置时运维接口只允许在服务器本机访问 |
| `LEDGER_AUTH_MODE` | `off` | 登录校验：`local` 内置账号（推荐）/ `off` 不校验（任何人可访问，**只适合本机试用**：监听非本机地址时服务拒绝启动）/ `gateway` 用请求头 `x-user-token` 向网关校验 / `proxy` 信任反向代理注入的身份头。详见「登录与权限」 |
| `LEDGER_AUTH_URL` | 无 | `gateway` 模式必填：网关的用户信息接口（前端用的 `/current_user`），返回 `{ code: 200, data: { id, username, accountName, superAdmin, tenantAdmin } }` |
| `LEDGER_AUTH_CA_FILE` | 无 | `gateway` 模式：网关的 HTTPS 证书由内部 CA 签发时，填 CA 根证书（PEM 文件，可含多个）的路径；程序只内置公共根证书，不配置会无法登录。路径或内容有误时服务启动失败并说明 |
| `LEDGER_AUTH_CACHE_SECS` | `60` | 令牌校验结果的缓存秒数，令牌在网关被吊销后最多这么久仍然有效 |
| `LEDGER_ADMINS` | 无 | 管理员的用户 id 或登录名（逗号分隔）；网关标记为超级管理员 / 租户管理员的用户自动是管理员 |
| `LEDGER_TRUSTED_PROXIES` | `127.0.0.1,::1` | `proxy` 模式下可信的反向代理地址，只有这些来源发来的身份头才被采信 |
| `LEDGER_AUDIT_DAYS` | `365` | 操作审计保留天数 |
| `LEDGER_REQUIRE_2FA` | 空 | `1`：所有内置账号必须开启两步验证（没开启的只能设置两步验证），见「登录与权限 → 两步验证」；需要 `LEDGER_AUTH_MODE=local` |
| `LEDGER_ALLOW_SELF_APPROVE` | `false` | 允许自己审批自己提交的单据（文件审批、月结）；小团队一人兼任时设为 `true` |
| `LEDGER_CORS` | 关闭 | 前端单独部署时填前端地址（多个逗号分隔）；页面由本服务提供时不需要 |
| `LEDGER_EMBED_ORIGINS` | 空 | 允许用 iframe 把**分享页**（`/share/…`）嵌入的网站来源，逗号或空白分隔：`https://a.example.com`、`https://*.example.com`、`http://localhost:3000`，或单独一个 `*`（任意网站）。空表示只允许本站页面嵌入。其他页面（编辑器、登录页、首页）永远只允许同源嵌入（防点击劫持）。只对本服务直接提供的页面（设置了 `LEDGER_WEB_DIR`）有效，nginx 自己提供页面时见「分享链接」一节 |
| `LEDGER_SLOW_REQUEST_MS` | `3000` | 处理时间超过这个毫秒数的请求记入日志（慢请求）；`0` 关闭。见「监控指标与日志」 |
| `LEDGER_LOG_FORMAT` | 文本 | 设为 `json` 时日志每行一个 JSON |
| `LEDGER_ALLOW_NO_AUTH` | `false` | 明确放行「不登录 + 对外监听（或 `LEDGER_CORS=*`）」。默认遇到这种配置服务**拒绝启动**；只有确认已由内网隔离 / 反向代理鉴权等手段保护时才设为 `1`，启动日志里仍会警告 |
| `LEDGER_INBOX_ROOTS` | 数据目录下 `inbox/` | 「数据连接 → 文件夹」可以收取的目录、「外部数据集」可以直接查询的 Parquet 文件所在的目录（多个用逗号分隔，如挂载的共享盘 `/mnt/share/抖店导出`）；只能选这些目录及其子目录 |
| `LEDGER_CONNECTOR_MAX_ROWS` | `20000000` | 数据连接单次同步的行数上限 |
| `LEDGER_PACKS` | 自动 | 场景包。目前有 `ecommerce`（电商资金台账：导入抖店资金流水、店铺档案、月结锁账与审批、余额勾稽、提现 / 银行对账、经营分析，以及内置的「资金流水」数据集和相关模板）。**不设置时自动判断**：库里已经有台账数据就启用（老部署升级后功能不会消失），全新的库不启用，界面和接口里就没有这些入口（访问相关接口得到 404）。明确指定：`LEDGER_PACKS=ecommerce` 启用；`LEDGER_PACKS=none` 全部关闭（库里的台账数据不会被删除，重新启用即可恢复）。改了要重启服务 |
| `LEDGER_URL_IMPORT` | 开启 | 「导入数据 → 从网址导入」由服务端下载文件；不希望服务器访问其他网址时设为 `off` |
| `LEDGER_URL_BLOCK_PRIVATE` | 关闭 | 服务端代用户访问网址（网址导入、定时推送的 Webhook）时，**始终拒绝**本机、链路本地（含 `169.254.169.254` 云元数据）、运营商 NAT（`100.64.0.0/10`，含阿里云元数据 `100.100.100.200`）、组播地址，IPv4 映射的 IPv6 写法同样处理；域名在连接时再检查一次（防 DNS 重绑定），重定向的每一跳也检查。私有部署里内网地址（`10/8`、`172.16/12`、`192.168/16`）默认允许；平台对公网开放时设为 `1` 一并拒绝。`LEDGER_URL_IMPORT_ALLOW_LOCAL=1` 取消全部限制，只用于本机开发 |
| `LEDGER_SECRET_KEY` | 自动生成 `secret.key` | 加密数据连接里数据库密码、定时推送的机器人地址 / 加签密钥的密钥（64 位十六进制）；不设置时首次启动在数据目录生成 `secret.key` |
| `LEDGER_PUBLIC_URL` | 不设置 | 用户访问平台的地址（如 `https://bi.example.com`）；设置后定时推送消息里带「查看完整看板」链接 |
| `LEDGER_SMTP_HOST` | 不设置 | 定时推送的发件服务器（如 `smtp.exmail.qq.com`）；不设置时不能使用邮件渠道 |
| `LEDGER_SMTP_PORT` | `465` | 发件端口 |
| `LEDGER_SMTP_TLS` | 465 端口为 `tls`，其他为 `starttls` | 加密方式：`tls` / `starttls` / `none`（`none` 仅限内网中继） |
| `LEDGER_SMTP_USER` / `LEDGER_SMTP_PASSWORD` | 不设置 | 发件账号与密码（企业邮箱一般需要「客户端专用密码」） |
| `LEDGER_SMTP_FROM` | 同 `LEDGER_SMTP_USER` | 发件人，可写成 `经营报表 <report@example.com>` |
| `LEDGER_SQL_TIMEOUT_SECS` | `60` | 「SQL 查询」的执行时限（秒），超时自动中止 |
| `LEDGER_TRASH_DAYS` | `30` | 删除的工作簿和数据集在回收站保留的天数（期间数据仍占用磁盘、参与备份），到期自动彻底删除；`0` 表示一直保留，直到手动彻底删除 |
| `LEDGER_AI_BASE_URL` | 不设置 | AI 助手的模型接口（OpenAI 兼容，不含 `/chat/completions`），如内网 vLLM `http://vllm.internal:8000/v1`、Ollama `http://127.0.0.1:11434/v1`、DeepSeek `https://api.deepseek.com/v1`；不设置时 AI 助手不可用 |
| `LEDGER_AI_MODEL` | 不设置 | 模型名，如 `qwen2.5-72b-instruct`、`deepseek-chat`；**需支持工具调用（function calling）** |
| `LEDGER_AI_API_KEY` | 不设置 | 模型接口密钥（内网模型多数不需要） |
| `LEDGER_AI_STREAM` | 开启 | 流式返回；个别部署不支持「流式 + 工具调用」时设为 `0` |
| `LEDGER_AI_MAX_STEPS` | `10` | 一次提问最多调用工具的轮数 |
| `LEDGER_AI_TEMPERATURE` | `0.2` | 模型的采样温度（分析类任务要稳定，一般不用改） |
| `LEDGER_AI_TIMEOUT_SECS` | `180` | 单次模型请求超时 |
| `RUST_LOG` | `gridlake=info,tower_http=info` | 日志级别 |

配置写错时服务不会启动，`journalctl -u gridlake` 中会说明是哪一项。

### 页面配置 `/opt/gridlake/web/config/index.js`

```js
window.__gridlake_config = {
  "ledgerApi": "",     // 表格服务地址；页面由表格服务提供时留空
  "loginUrl": "",      // 网关登录模式：未登录时跳转的统一登录地址（会带上 redirect 参数）
  "tokenCookie": ""    // 网关登录模式：网关写入登录令牌的 cookie 名（默认 gridlake-token；项目原名 WebExcel 时是 webexcel-token，沿用旧名的部署在这里填 webexcel-token）
}
```

修改后浏览器刷新即可生效（该文件不缓存），升级时 `install.sh` 会保留这个文件。

### HTTPS / 统一域名（可选，前置 nginx）

```nginx
server {
    listen 443 ssl http2;
    server_name excel.example.com;
    ssl_certificate     /etc/nginx/ssl/excel.pem;
    ssl_certificate_key /etc/nginx/ssl/excel.key;

    client_max_body_size 1024m;        # 与 LEDGER_MAX_UPLOAD_MB 一致
    proxy_read_timeout   600s;         # 大文件导入、导出

    location / {
        proxy_pass http://127.0.0.1:8787;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;   # 内置账号登录的会话 cookie 据此加 Secure 标记
        proxy_buffering off;           # 流式导出
    }
}
```

此时 `LEDGER_ADDR=127.0.0.1:8787`，只让 nginx 访问。经 nginx 转发的请求带 `X-Forwarded-For`，运维接口会拒绝（需在服务器本机直接访问 8787，或配置 `LEDGER_ADMIN_TOKEN`）。

## 四、备份与恢复

**自动备份**：每天 `LEDGER_BACKUP_AT` 生成 `backups/ledger-YYYYMMDD-HHMMSS.duckdb`，是一份完整、可直接使用的数据库文件，生成后逐表核对行数；保留最近 `LEDGER_BACKUP_KEEP` 份。建议再用公司的备份系统把 `backups/` 同步到异地，或者直接让服务备份完成后上传到对象存储：

**备份上传到对象存储**：设置 `LEDGER_BACKUP_S3_BUCKET` 等变量后（AWS S3，或 MinIO、阿里云 OSS、腾讯云 COS 等兼容 S3 协议的存储），每次备份（自动的和手动的）生成本地文件后会上传到 `s3://桶/前缀/ledger-….duckdb`。要点：

- 为它单独建一个**只管这个桶（或前缀）的密钥**：需要 `s3:PutObject`、`s3:GetObject`（核对大小用）、`s3:ListBucket`、`s3:DeleteObject`（清理旧备份）、`s3:AbortMultipartUpload`；
- 文件超过 64 MB 自动分片上传（每片 64 MB，上传失败会中止，不留半截对象），上传后用 HEAD 核对大小与本地一致；上传期间不占用导入锁，不影响正常使用；
- 对象存储上只保留最近 `LEDGER_BACKUP_S3_KEEP` 份，只清理 `ledger-*.duckdb`，同前缀下别的对象不动；本地的保留份数仍由 `LEDGER_BACKUP_KEEP` 决定；
- **上传失败不会让本地备份失败**，但这次备份在 `/api/admin/status` 里会带 `remoteError`，监控指标 `gridlake_last_backup_success` 变为 0，请据此告警；
- **不会上传 `secret.key`**（它和备份放在同一个地方就等于没加密）：请单独保管，换服务器恢复时放回数据目录；
- 内部 CA 签发的 https 证书同样用 `LEDGER_AUTH_CA_FILE`；
- 从对象存储恢复：先把备份文件下载到服务器（`aws s3 cp` / `mc cp` 等），再用下面的 `gridlake restore <文件>`。

**手动备份**（服务运行中，在服务器本机执行）：

```bash
curl -X POST http://127.0.0.1:8787/api/admin/backup
# 配置了令牌时：curl -X POST -H "x-admin-token: <令牌>" http://服务器:8787/api/admin/backup
```

**恢复**：

```bash
systemctl stop gridlake
sudo -u gridlake env $(grep -v '^#' /etc/gridlake/ledger.env | xargs) \
  /opt/gridlake/bin/gridlake restore /var/lib/gridlake/backups/ledger-20261004-023000.duckdb
systemctl start gridlake
```

恢复前会校验备份文件；当前数据文件改名保留为 `ledger.duckdb.before-restore-<时间>`，确认无误后可手动删除。

**恢复演练（验证备份真的能用）**：备份没恢复过就不算可靠。三道检查：

- **每次备份后自动做**：生成备份后立刻用恢复时相同的方式（只读打开这个文件）重新验证——是 gridlake 的数据文件、数据结构版本不比当前程序新、数据集定义没有损坏、每张数据表都读得出行数。通不过的备份会被改名为 `…duckdb.failed`（不会被当作可用备份，也不会上传），这次备份算失败（`gridlake_last_backup_success` 为 0）；结果在 `/api/admin/status` 的 `lastBackup.verify`；
- **随时手动演练**：`curl -X POST "http://127.0.0.1:8787/api/admin/backup/verify"` 验证本地最新的备份；`?source=remote` 把对象存储上最新的备份下载回来验证（临时文件验证后删除）；`?full=true` 再把每张表的每一列整个读一遍，校验所有数据块（亿级数据要几分钟，建议每周或每月跑一次，放在业务低峰）。需要运维令牌的规则同手动备份；
- **命令行**：`gridlake verify <备份文件> [--full]`，只读打开，服务运行中也能执行（拿别处下载的备份文件先验一遍）。`gridlake restore` 在恢复前也会先做同样的检查。

演练验证的是「备份文件能打开、内容读得出来」，不替代真正的恢复演练——建议每季度在一台测试机上用 `gridlake restore` 恢复一份备份并启动服务点开看看。

**数据连接的密钥**：数据连接里保存的数据库密码用 `数据目录/secret.key` 加密。每次备份会把它复制到备份目录（`backups/secret.key`）。
换服务器恢复时，把 `secret.key` 一并放回数据目录，否则需要在「数据连接」里重新填写各数据库的密码。备份目录同步到异地时注意保管好这个文件。

### 登录与权限（可选）

默认 `LEDGER_AUTH_MODE=off`：不校验身份，任何能访问页面的人都可以使用全部功能，**只适合本机试用**——监听非本机地址（或 `LEDGER_CORS=*`）时服务会拒绝启动（确认已有内网隔离 / 反向代理鉴权等保护时，才用 `LEDGER_ALLOW_NO_AUTH=1` 放行）。要用于真实数据，开启登录：

| 方式 | 配置 | 适合 |
|---|---|---|
| **内置账号**（推荐） | `LEDGER_AUTH_MODE=local` | 没有统一登录的团队：管理员在首页「自动化 → 账号管理」里建账号 |
| 内置账号 + **单点登录（OIDC）** | `LEDGER_AUTH_MODE=local` + `LEDGER_OIDC_*` | 公司有 Keycloak / Okta / Azure AD / Authentik / Casdoor 等：登录页多一个「用公司账号登录」，首次登录自动建账号 |
| 对接登录网关 | `LEDGER_AUTH_MODE=gateway` + `LEDGER_AUTH_URL` | 已有统一登录：浏览器带的令牌由本服务转给网关校验 |
| 反向代理传入身份 | `LEDGER_AUTH_MODE=proxy` | 用 nginx `auth_request`、OAuth2 Proxy 等接企业单点登录（OIDC / LDAP） |

**内置账号**：

```
LEDGER_AUTH_MODE=local
LEDGER_ADMIN_USER=admin            # 首次启动时创建的管理员用户名（默认 admin）
LEDGER_ADMIN_PASSWORD=请改成强密码   # 不设置则随机生成，只在首次启动的日志里打印一次
LEDGER_SESSION_DAYS=7              # 登录有效天数
```

- 首次启动（还没有任何账号）时自动创建管理员；之后改这两个变量不会影响已有账号，密码在页面里改
- 密码以 PBKDF2-SHA256（60 万次迭代、随机盐）保存，登录令牌只存哈希；同一用户名 10 分钟内失败 5 次后暂时拒绝登录（失败次数存在数据库里，重启服务不会清零）；登录成功与失败都记入操作审计
- 管理员可以新建账号、设为管理员、停用、重置密码；停用或重置密码后，对方已登录的设备立即退出。账号不能删除（创建的工作簿、审批与审计要能追溯），至少保留一个可用的管理员
- 用户点右上角自己的名字可以修改密码、退出登录
- **会话 cookie**：浏览器登录后，服务端写入 `gridlake_session` cookie（`HttpOnly`、`SameSite=Lax`；经 HTTPS 反向代理访问时加 `Secure`，依据代理传来的 `X-Forwarded-Proto`，也可用 `LEDGER_COOKIE_SECURE=1/0` 强制），页面脚本读不到令牌。用 cookie 登录的写请求必须带 `x-requested-with` 请求头（前端已自动带上），防跨站请求伪造
- **脚本 / 前后端分开部署**：登录接口响应里也返回 `token`，放进 `x-user-token` 请求头即可调用接口（这种方式不依赖 cookie，也不需要 `x-requested-with`）；前后端不同源时页面也是这样工作的
- **个人访问令牌（脚本、CI 长期调用用）**：登录会话几天就过期，不适合定时脚本。右上角用户菜单 →「访问令牌」创建一个（`glp_` 开头），权限与你的账号完全相同，可设有效期（30 天 / 90 天 / 1 年 / 永不过期）、随时吊销，账号被停用后立即失效。**令牌只在创建时显示一次**，库里只存摘要，丢了只能重建。用法：

  ```bash
  curl -H "Authorization: Bearer glp_xxxxxxxx" https://你的地址/api/ledger/workbooks
  # 也可以放在 x-user-token 请求头里；scripts/seed-demo.py 的 --token 同样可以直接用它
  ```

  **只读令牌**：创建时勾选「只读令牌」得到 `glr_` 开头的令牌（接口里 `readOnly: true`），只能读取数据——GET / HEAD，以及 SQL 查询、数据集的游标 / 统计 / 透视 / 聚合 / 试算这类「带复杂条件但不改数据」的 POST；其余写操作一律返回 403。适合报表、监控、给第三方看数据的脚本，泄露了也改不了数据。「只读」写在令牌前缀里，不能通过改前缀升级成完全权限（摘要对不上）；旧版程序不认识 `glr_`，回退版本后这类令牌只会失效，不会变成完全权限。
  **限定数据集**：创建时在「可访问的数据集」里选几个（接口里 `datasets: [数据集 id…]`，最多 50 个），令牌就只能访问这些数据集——取行、游标、统计、取值、聚合（公式下推，按 id 或名称都认）、透视、导出、写入；列表接口只返回它们；改定义 / 删除 / 计算列、SQL、工作簿、令牌、账号等其余接口一律 403（登记表默认拒绝）。适合只往某一张表写数据的采集脚本、只给某个看板取数的服务；泄露后也碰不到别的数据集。可以和「只读令牌」叠加（只读 + 限定 = 只能读这几个数据集）。限定到的数据集在创建时检查（必须存在、且你自己看得到）；数据集改名后限定范围跟着新名称走（最多 30 秒生效）；数据集被删除后令牌对它自然没用。数据文件结构版本因此升到 5，升级后旧版本程序不能再打开这个数据文件（否则限定了数据集的令牌会变成能访问全部数据集）

  限制：只在 `LEDGER_AUTH_MODE=local` 下可用；每个账号最多 20 个；**不能用令牌创建或吊销令牌**（令牌泄露后攻击者没法给自己再造一批，需要在网页里登录操作）；创建与吊销记入操作审计。令牌等同密码，不要写进代码仓库，泄露了立刻吊销

**单点登录（OIDC）**：在内置账号上叠加，登录页多一个「用 XX 登录」按钮（密码登录仍保留，作为应急入口）。授权码 + PKCE，身份提供方只要支持 OIDC Discovery 即可：

```
LEDGER_AUTH_MODE=local
LEDGER_OIDC_ISSUER=https://idp.example.com/realms/corp      # 必填，https；能访问到 <issuer>/.well-known/openid-configuration
LEDGER_OIDC_CLIENT_ID=gridlake                              # 必填
LEDGER_OIDC_CLIENT_SECRET=...                               # 机密客户端的密钥；公开客户端（只靠 PKCE）不设
LEDGER_OIDC_REDIRECT_URL=https://你的域名/api/ledger/auth/oidc/callback   # 必填，要与身份提供方里登记的回调地址完全一致
LEDGER_OIDC_NAME=公司账号              # 登录按钮上的名字（默认 SSO）
LEDGER_OIDC_ADMIN_GROUP=gridlake-admins   # 可选：属于这个组的人是管理员（每次 SSO 登录时同步）
```

- **在身份提供方里**登记一个客户端，授权码模式，回调地址就是上面的 `LEDGER_OIDC_REDIRECT_URL`（经反向代理的话填对外域名下的完整地址，路径以实际代理为准，例如 `/ledger-api/api/ledger/auth/oidc/callback`）。需要的 scope 默认是 `openid profile email`（`LEDGER_OIDC_SCOPES` 可改，必须含 `openid`）
- **账号对应关系**：身份提供方里的 `(issuer, sub)` 对应一个内置账号。**第一次**SSO 登录自动建账号（用户名取 `preferred_username`，可用 `LEDGER_OIDC_USERNAME_CLAIM` 改；没有就取邮箱 `@` 之前，再没有取 `sub`；姓名取 `name`，可用 `LEDGER_OIDC_NAME_CLAIM` 改），重名时自动加 `-2`、`-3`。之后的权限、数据范围、审批、审计都和内置账号完全一样。SSO 建出的账号没有密码，不能用密码登录；管理员仍可在「账号管理」里停用它（停用后 SSO 也登录不了），停用即时生效
- **不会把身份提供方的用户绑到同名的本地账号上**（否则身份提供方里能注册同名用户的人就能顶替本地管理员）。要把已有的本地账号迁到 SSO：设 `LEDGER_OIDC_LINK_BY_USERNAME=1`，第一次 SSO 登录时把身份绑到**同名且还没绑过身份**的本地账号，迁完记得关掉。不想自动建账号：`LEDGER_OIDC_AUTO_CREATE=0`，此时没有绑定过的人登录会提示「账号还没有开通」
- **管理员**：设了 `LEDGER_OIDC_ADMIN_GROUP` 后，每次 SSO 登录按组声明（`LEDGER_OIDC_GROUPS_CLAIM`，默认 `groups`；id_token 里没有时到 userinfo 接口补）同步该账号的管理员身份；只同步经 SSO 绑定的账号，本地建的管理员（应急用）不受影响，且不会把最后一个管理员降级。不设就完全在「账号管理」里手动指定
- **安全**：state 同时存在服务端和浏览器 cookie 里（防登录 CSRF）、PKCE、nonce；id_token 由服务端直接向令牌接口（HTTPS）换取并校验 `iss` / `aud` / `exp` / `nonce`（OIDC 规范允许此时不再验签），所以签发者地址必须是 `https`——内网明文部署要显式设 `LEDGER_OIDC_ALLOW_HTTP=1`（本机回环地址除外）；失败时浏览器只看到一个简短的错误代码，细节在服务日志里。登录成功后的跳转只允许站内路径
- 身份提供方用内部 CA 签发 HTTPS 证书时，同样用 `LEDGER_AUTH_CA_FILE` 提供根证书
- **限制**：要求页面与服务**同源**部署（默认的安装包 / Docker / nginx 同域都是），因为登录结果靠服务端写的 cookie 带回页面；**退出登录只退出本系统**，不会通知身份提供方（那边还登录着的话，再点 SSO 按钮会直接进来）；暂不支持 SAML / LDAP

**两步验证（TOTP）**：内置账号可以在右上角用户菜单 →「两步验证」自己开启：登录时除了密码，还要输入验证器 App（Google Authenticator、Microsoft Authenticator、1Password、Authy 等）里的 6 位动态码。要点：

- **开启**：点「开始设置」→ 把显示的密钥（或 `otpauth://` 地址）加到验证器 App → 输入 App 里现在显示的 6 位数字确认 → 保存页面上显示的 **10 个一次性恢复码**（只显示这一次；手机丢了时可以代替验证码登录，每个只能用一次）；
- **登录**：输入用户名密码后，页面会再要验证码；动态码只能用一次（防止被偷看后重放），允许前后各 30 秒的时钟误差，所以手机时间要准；
- **防暴力穷举**：输错的验证码和输错密码一样计入失败次数（同一用户名 10 分钟内 5 次锁定）；密码错误时的提示不会透露这个账号有没有开启两步验证；
- **停用**：用户自己在同一个对话框里停用，要再输入密码和一个验证码（或恢复码）；**手机丢了又没有恢复码**：管理员在「账号管理」里点「重置两步验证」，对方已登录的设备会退出，之后只需要密码，可以自己重新开启；
- 密钥以密文存库（与数据连接共用 `secret.key` 加密），恢复码只存摘要；个人访问令牌是独立的凭证，不受两步验证影响，**但不能用访问令牌设置或停用两步验证**；单点登录（OIDC）的账号由身份提供方负责二次验证，不需要在这里开启；
- **强制所有人开启**：设置 `LEDGER_REQUIRE_2FA=1`（需要 `LEDGER_AUTH_MODE=local`）。没开启两步验证的内置账号仍可用密码登录，但登录后界面会弹出不能关闭的设置对话框，服务端除了设置两步验证、改密码、退出之外的接口一律返回 403，设置完成并保存恢复码后才能继续使用。单点登录账号（由身份提供方负责二次验证）和**个人访问令牌**（脚本没法输入验证码）不受限制；但没开启两步验证的账号不能新建令牌。用户停用两步验证后会重新被要求开启；管理员重置某人的两步验证后，对方下次登录也会被要求重新设置
- **升级说明**：账号表新增了两步验证的列，**数据文件结构版本升到 3**（之后分享链接又加了访问密码列，版本升到 4）——升级后旧版本程序不能再打开这个数据文件（否则启用了两步验证的账号会只凭密码登录）。要回退请用升级前的备份恢复。

**对接登录网关**：

```
LEDGER_AUTH_MODE=gateway
LEDGER_AUTH_URL=https://网关地址/api/current_user
LEDGER_ADMINS=zhangsan
```

网关接口返回 `{ code: 200, data: { id, username, accountName, superAdmin, tenantAdmin } }`（也接受不带信封的对象）。在运行时配置里填 `loginUrl`（未登录时跳转的统一登录页）与 `tokenCookie`（网关写入令牌的 cookie 名）。

以下规则对三种登录方式都适用：

- **网关模式的身份**：浏览器请求带的 `x-user-token`（登录网关发的令牌）由本服务转给 `LEDGER_AUTH_URL` 校验，结果缓存 60 秒。网关不可用时返回 503「无法连接身份服务」，不会放行；已缓存的令牌在缓存期内仍可用
- **前端**：打开在线表格页面前先确认登录，未登录跳转登录页，登录后回到原页面；操作人固定为登录账号，月结中心里不再手填
- **工作簿**：新建的归创建人，默认仅自己可见，所有者可改为「所有人可查看」或「所有人可编辑」；只有所有者与管理员能删除、改共享范围；别人共享给你的只读工作簿打开时有「只读」标记。登录校验启用前创建的工作簿没有所有者，按「所有人可编辑」使用，只有管理员能删除
- **数据集**：所有人可以查看、透视、导出；改名、删除、改结构（计算列、关联视图）、整体替换导入只有所有者与管理员（内置数据集与启用前创建的只有管理员）。行级权限（按店铺过滤）尚未提供
- **数据权限**：见下一节「数据权限：按某一列的取值限制数据」
- **审批**：文件审批与月结审批的审批人从「用户目录」里选：内置账号建好即在目录里；网关 / 代理模式的新同事需要先登录一次才能被选为审批人。只有指定审批人（或管理员代为处理，会留痕）能审批；**提交人不能审批自己的单据**，月结的反结账也只有审批人或管理员能做（小团队一人兼任时设 `LEDGER_ALLOW_SELF_APPROVE=true`）。审批人对被审批的工作簿自动获得查看权限
- **仅管理员**：数据连接的新建 / 修改 / 同步 / 测试、推送渠道、外部 AI（MCP）令牌、清空回收站、删除店铺流水、查看操作审计
- **操作审计**：登录用户的写操作与导出（含被拒绝的）记入数据库，管理员在首页「自动化 → 操作审计」查看，保留 `LEDGER_AUDIT_DAYS` 天；读取类请求不记
- **管理员**：内置账号里设为管理员的；网关里标记为超级管理员 / 租户管理员的；加上 `LEDGER_ADMINS` 中列出的 id 或登录名
- **网关用 HTTPS 且证书是内部 CA 签发的**：设置 `LEDGER_AUTH_CA_FILE` 指向 CA 根证书（PEM）。不设置时登录会失败，页面提示「无法连接身份服务…网关的 HTTPS 证书不被信任」
- **网关接口要求签名时**（前端配置里 `apiSign` 为 true，服务端直接调用 `LEDGER_AUTH_URL` 可能被网关拒绝；本次未能连真实网关验证，上线前请先试）：改用 `LEDGER_AUTH_MODE=proxy`，由 nginx `auth_request` 校验后注入 `x-auth-user-id`、`x-auth-user-name`（URL 编码）、`x-auth-user-admin`（`1` 表示管理员），并让本服务只接受来自 nginx 的连接（`LEDGER_TRUSTED_PROXIES` 填 nginx 的地址）
- **不要把本服务端口直接暴露给用户**：gateway 模式下直连也要令牌，proxy 模式下非可信地址发来的身份头一律拒绝；但 off 模式没有任何保护

### 数据权限：按某一列的取值限制数据（可选）

登录校验开启后，管理员可以限制某些用户只能看到某些行。入口：首页「自动化 → 数据权限（行级）」，或编辑器左下角「数据中心 → 数据权限」。

**概念**：
- **维度**是一个名字，代表「按哪类取值划分范围」，比如 `店铺`、`地区`、`部门`。随便起，在规则里输入新名字就建好了。
- **规则**：给用户（或「默认规则」）在某个维度上指定可见的取值。一个用户可以在几个维度上同时受限。
- **数据集绑定**：每个数据集指定「按哪个维度的哪一列过滤」，或设为「所有人可见」。所以**同一个用户在不同数据集上受不同规则限制**：订单表按「店铺」维度的店铺列，区域销售按「地区」维度的地区列。

**配置步骤**：
1. **绑定数据集**（「数据集」页签）：选「按列过滤」后选一列和一个维度（维度不选按「店铺」）。资金流水固定按店铺列。**没有设置的数据集，受限用户看不到**
2. **设置用户范围**（「用户范围」页签）：选用户、选维度、填可见的取值（用户需要先登录过一次才能被选到）。「默认规则」按维度生效，适用于在这个维度上没有单独规则的用户；用户自己的规则（哪怕是「不限」）优先于默认规则。管理员和没有规则的用户不受限，所以先配置用户、再按需设置默认规则即可，不会把所有人锁在外面
3. **某个数据集绑定的维度上，用户没有规则（不受限）时，这个数据集对他整体可见**——只限制「地区」的用户，照样能看到全部的「订单」（它按店铺维度过滤）
4. 受限用户读取数据集、透视、公式、SQL、AI 助手、导出时只看到范围内的行。**导入数据、建视图、定时推送、阈值告警、数据连接等会绕过过滤的功能对他们关闭**（收集任务的负责人就是这样的受限用户，见「多人填报」），页面上相应入口也会隐藏；填报只能填按某个维度划分范围的数据集，而且只能填自己范围内的行
5. 修改立即生效；变更都记在操作审计里

注意：
- 取值要与数据里的值完全一致（店铺维度可从店铺档案里选，其他维度手输）
- 已经写进工作簿单元格里的数值不受限：管理员做好的工作簿共享给受限用户（可见范围「查看 / 编辑」）时，对方能看到里面已有的数字
- 外部 AI（MCP）令牌、已有的定时推送与阈值告警按服务账号运行，不受创建人的范围限制
- 一个数据集只能绑定一个维度；需要「既按店铺又按地区」限制同一个数据集时，目前要拆成两层（比如先建一个按地区过滤的关联视图）。接口里旧的写法（`mode=shops`、`shops` 字段）仍然可用，等同于「店铺」维度
- **升级说明**：规则存储从旧表搬到了新表，数据文件结构版本升到 2——升级后旧版本程序不能再打开这个数据文件（否则读不到新规则，会悄悄放开限制）。要回退请用升级前的备份恢复

### 数据连接（自动同步）

页面「数据连接」可以按计划从以下来源自动同步数据：

| 来源 | 部署要求 |
|---|---|
| 文件夹 | 目录必须在 `LEDGER_INBOX_ROOTS` 之内；共享盘先挂载到服务器（如 `mount -t cifs //文件服务器/抖店导出 /mnt/share/抖店导出 -o ro,...`），服务账号 `gridlake` 需要有读权限。只读取，不修改、不删除源文件 |
| 对象存储（S3） | AWS S3，以及兼容 S3 协议的 MinIO、阿里云 OSS、腾讯云 COS、华为云 OBS、Cloudflare R2 等。服务器能访问存储服务的地址；**建议为平台单独建一个只读密钥**（只需要 `s3:ListBucket` 与 `s3:GetObject`）。填存储桶、访问密钥、前缀（如 `reports/2026/`）和文件名规则（如 `流水_*.csv`，可勾选「包含子目录」）；用 AWS S3 时「服务地址」留空并填区域，自建或其他云填服务地址（只写主机和端口，如 `https://minio.corp:9000`）。地址风格「自动」：填了服务地址用路径风格（`地址/桶/键`，MinIO 适用），AWS 用虚拟主机风格；阿里云 OSS 等只支持虚拟主机风格的请选「虚拟主机风格」。每个对象只导入一次（对象键 + 大小 + 修改时间），对象被覆盖后会重新导入；最近 1 分钟内修改的对象视为可能仍在上传，下一轮再收；单个对象不能超过上传上限 `LEDGER_MAX_UPLOAD_MB`；一个前缀下最多扫描 2 万个对象，再多请把前缀写具体。密钥加密后存储，界面和接口都不会再返回。请求用 AWS Signature V4 签名，存储用内部 CA 签发的 https 证书（自建 MinIO 常见）时，把 CA 根证书（PEM）放到服务器上并设置 `LEDGER_AUTH_CA_FILE`（网关校验、单点登录的身份提供方和对象存储共用这一个文件）；证书必须是 CA 签发的，**不能直接拿自签的服务器证书当根证书** |
| MySQL / MariaDB、PostgreSQL | 服务器能访问数据库端口；**建议为平台单独建一个只有 SELECT 权限的账号**。平台只执行单条 SELECT，并在只读事务中执行 |

`gridlake.service` 开启了 `ProtectHome=true`：收件目录不要放在 `/home` 下；放在 `/var/lib/gridlake` 之外时无需额外配置（只读访问），systemd 会照常允许读取。

### 外部数据集（直接查询 Parquet 文件，不导入）

数据已经是 Parquet 文件（数据仓库、数据湖导出，或其他系统按天 / 按月写出的文件）时，管理员可以在「导入数据」对话框里选「直接查询服务器上的 Parquet 文件（不导入）」：填目录（必须在 `LEDGER_INBOX_ROOTS` 之内）和文件名规则（默认 `*.parquet`，可勾选包含子目录、把 `年=2026/月=09` 这样的目录名读成列），预览后创建。

- **不复制数据**：数据集是一个指向这些文件的只读视图，库文件不会变大；列类型取自 Parquet 文件本身（日期 / 时间戳按「2026-09-15 10:00:00」形式的文本显示，与导入的数据集一致）。
- **浏览快**：创建 / 刷新时记下每个文件的行数，浏览时只读当前这一屏所在的文件片段（实测 1000 万行上取一屏约 5 ~ 15 毫秒，筛选、排序后翻页也一样）；筛选、透视、公式下推、SQL 都在 DuckDB 里直接扫描文件，速度和导入后的数据集相当。
- **文件有增减或结构变化后**，在数据表上点「刷新文件列表」（只有管理员）：会报告新增 / 移除的文件和列，文件没变时什么都不动；刷新会让计算列或关联视图失效时整体取消。文件被移走 / 删除后，查询会提示「文件找不到了，请刷新文件列表」，数据集列表不受影响。
- **自动检查**：新建时或在数据表上点「设置…」选「每 5 分钟 / 15 分钟 / 每小时 / 每 6 小时 / 每天」，服务端到点比对文件列表、大小和修改时间（只看文件系统，不读 Parquet 内容，开销很小），**有变化才重新读取**——其他系统往目录里写新的分区文件后，数据集自动跟上。检查和导入串行进行；失败（目录不见了、刷新会让计算列失效……）不改动数据集，原因显示在「外部文件」标签的提示里（标签变红），下次到点再试。有变化时发出 Webhook 事件 `dataset.refreshed`（见「事件 Webhook」）。接口里可以设 1 ~ 1440 分钟。
- **修改读取方式**：「设置…」里可以改目录、文件名规则、子目录 / 分区选项，保存时按新规则重新读取（同样受计算列 / 关联视图保护），不用删了重建。
- **只读**：不能导入、填报写入；可以加计算列、建关联视图、透视、写公式和 SQL；数据权限（按列取值的行级权限）照常生效。
- 备份只包含数据集的定义，**不包含 Parquet 文件本身**；在另一台机器上恢复时，文件要放在相同的路径。
- 服务账号 `gridlake` 需要对文件有读权限；`ProtectHome=true` 的限制同上（不要放在 `/home` 下）。

### 外部 AI 接入（MCP）

页面「外部 AI 接入」：给 Claude、Cursor、Cherry Studio、Dify 等支持 MCP 的 AI 助手发放令牌，让它们**只读**查询数据集、仪表盘。

- 服务地址：`http(s)://平台地址/api/mcp`（与页面同一端口；经 nginx 转发时 `/api/` 已包含在内，无需额外配置）
- **访问控制**：没有令牌时接口不可用；令牌只显示一次，服务端只存摘要；每个令牌可限定数据集、是否允许 SQL，可随时吊销；所有调用记录在「调用记录」中（保留最近 5000 条）
- **数据出网提醒**：AI 客户端拿到的是查询结果（汇总数据、SQL 结果最多 50 行、仪表盘指标）。客户端若使用云端大模型，这些结果会发送给模型服务商；数据不能出网时，只给接入内网模型的客户端发令牌，并限定数据集
- Claude Desktop 的远程连接器要求 HTTPS；内网 HTTP 地址请用 `npx mcp-remote … --allow-http` 或程序自带的 `gridlake mcp-bridge` 转接（页面「接入方法」里有现成配置；地址和令牌也可以不写在命令行里，改用环境变量 `LEDGER_MCP_URL` / `LEDGER_MCP_TOKEN`）

### SQL 查询

页面「SQL 查询」：对数据集写只读 SQL（或用查询构建器生成），结果可另存为数据集并每天 / 数据同步后 / 某个数据集更新后重算。

- **「数据集更新后」**（SQL 重算、定时推送、阈值告警都可以选）：选定的数据集有新数据时触发——导入（追加、替换、按主键更新）、数据连接同步成功、外部数据集的文件有变化（手动刷新、自动检查、修改读取方式）。**填报提交不触发**（太频繁）。SQL 查询重算写入的结果数据集**只触发推送和告警，不会再触发别的 SQL 查询**，所以不会出现两个查询互相触发、停不下来的情况；典型链路是「订单导入新数据 → 汇总查询重算 → 汇总表更新后推送 / 检查告警」

- **只读与隔离**：只能执行一条查询语句，只能读数据集（通过临时视图，看不到平台内部表），不能读写服务器文件、访问网络、读取环境变量；每次执行在事务中并回滚；超过时限（`LEDGER_SQL_TIMEOUT_SECS`）中止
- 另存为数据集的结果与导入的数据集一样参与备份；结果行数上限与数据连接相同（`LEDGER_CONNECTOR_MAX_ROWS`）
- 查询消耗服务器 CPU / 内存，受 `LEDGER_MEMORY_LIMIT`、`LEDGER_THREADS` 约束；大表关联建议先汇总再关联

### AI 分析助手

页面右上「AI 助手」：用中文提问，助手调用平台的查询能力回答，并生成透视表、图表、公式、计算列建议（用户点「应用」才写入）。

- **模型**：任何 OpenAI 兼容、支持工具调用的接口。数据不出内网时推荐内网部署 Qwen2.5-72B-Instruct / Qwen3 / DeepSeek-V3（vLLM 启动时加 `--enable-auto-tool-choice --tool-call-parser hermes`）；7B 级小模型工具调用不稳定，不建议
- **发送给模型的内容**：数据集名称与列名、行数；文本列最多 8 个常见取值（如店铺名、动账场景）；汇总查询的结果（分组合计，最多 60 行）；用户勾选「附带当前界面」时的工作表名、选区内容（最多 20 行 × 10 列）。**不发送明细行**。使用云端模型时请确认这些内容可以出网
- 会话按工作簿保存在 `ledger_ai_thread / ledger_ai_message`，建议及「谁在何时应用」记录在 `ledger_ai_action`，随数据库一起备份
- 模型接口地址由管理员配置，服务端会直接访问（内网地址也可以），不受上面「始终拒绝」的地址限制；数据连接也只有管理员能建，同样不受限

### 定时推送

页面「定时推送」把仪表盘页的指标、排行按计划（每天 / 每周 / 每月 / 数据连接同步后）推送出去（也可以选「某个数据集更新后」，见上面「SQL 查询」一节）：

| 渠道 | 部署要求 |
|---|---|
| 企业微信 / 钉钉 / 飞书群机器人 | 服务器能访问 `qyapi.weixin.qq.com` / `oapi.dingtalk.com` / `open.feishu.cn`（出网 443）；内网环境在出口代理或防火墙放行这三个域名。钉钉、飞书建议开启「加签」 |
| 邮件 | 配置上表的 `LEDGER_SMTP_*`；服务器能访问 SMTP 端口（465 / 587） |

- 推送内容由服务端按工作簿**已保存**的版本计算，切片器的「本月」「近 30 天」按发送当天计算；未保存的修改不会出现在推送里
- 配置 `LEDGER_PUBLIC_URL` 后，消息里的「查看完整看板」直接打开对应的仪表盘页
- 机器人地址和加签密钥用 `secret.key` 加密保存（与数据连接相同）；推送记录保留每个任务最近 100 次
- 推送时间按服务器时区；`timedatectl` 确认服务器时区为 Asia/Shanghai

### 多人填报（收集任务）

页面「自动化 → 收集任务」（管理员）让很多人往**同一个数据集**里各填各的，看板上看谁填了、谁没填。典型场景：几十家店铺 / 部门每周或每月报一次数据。

1. 新建任务：定义填报表的列（或选一个已有的数据集），列出**填报单位**（如店铺）并指派**负责人**（登录过一次系统的用户；批量粘贴「单位,账号名」更快）。新建的填报表会自动带上「填报单位」「期次」两列，主键 = 单位 + 期次 + 业务主键；已有的数据集主键必须包含这两列，否则不同单位 / 不同期的数据会互相覆盖
2. 开启一期（如 2026-10）。期次必须已开启、单位必须在任务里才能提交
3. **负责人在「首页 → 自动化 → 我的填报」里点「去填报」**：服务端为（任务、单位、期次）一键生成一个填报工作簿并打开，填报区已经放好——「填报单位」和「期次」是填报区的**固定列**，不显示在表格里、提交时自动带上，负责人只填其他列；数据集里这个单位这一期已有的行会预填进去。同一个人对同一个单位同一期只生成一次，再点直接打开；管理员可以为任何单位生成（代填）。工作簿归生成的人，默认仅自己可见。也可以自己在任意工作簿里用工具栏「填报」放填报区，但列里要带上单位列和期次列
4. 看板按「单位 × 期次」显示状态（未提交 / 待确认 / 已退回 / 已确认）、提交人、已填行数，可以复制未提交名单去催办；汇总不用另做，透视表和仪表盘直接引用这个数据集
5. **审核（可选）**：任务里可以指定一个**确认人**（登录过一次系统的用户，管理员始终也能审核）。负责人提交后单位显示「待确认」，确认人在看板（负责人和确认人都能从「首页 → 我的填报」里进，确认人点「去确认」）里看过数据后：
   - **确认**：这个单位这一期**锁定**——提交和按主键删除都被拒绝（管理员也一样），要改得先「撤销确认」或「退回」。支持「确认全部待确认的」一次确认多个，一批里有一个不行就整批不变
   - **退回**：必须写原因（不超过 200 字）；已提交或已确认的都能退回。负责人在「我的填报」里看到「已退回」和原因，也会收到通知（顶栏铃铛，点开直接回到「我的填报」）；改完重新提交，状态回到「待确认」
   - **撤销确认**：回到「待确认」，负责人又能改了
   - 确认和退回都会通知负责人，操作进审计日志（「审核填报」）
6. **截止日期与催办（可选）**：开启期次时（或之后在看板里「设置截止日期」）可以设一个截止日期。当天 24 点前都算按时，过了还没提交（含被退回没改好的）显示「逾期」，看板、「我的填报」、任务列表都会标出来——**只是提示，不拦截提交**。催办有两种：
   - **手动**：看板上点「催办未提交的」或某一行的「催办」（管理员或确认人）。负责人收到站内通知（顶栏铃铛，点开回到「我的填报」）；同一个单位 1 小时内不重复催，看板上记着上次催办时间。没有指派负责人的单位无处可催，只出现在群里的名单里
   - **自动**：设了截止日期的期次，每天 9 点以后自动催一次没提交的单位——截止前一天、截止当天、逾期后每天（最多 7 天）。每 10 分钟检查一次，服务器时区同「定时推送」；改了截止日期（延期）后催办记录清空，会重新催
   - **推送到群 / 邮箱（可选）**：任务里勾选「催办推送到」（渠道在「定时推送」里配置，企业微信 / 钉钉 / 飞书群、邮件），催办时把「没提交的名单」（单位、负责人、状态、截止说明）也推过去；每个期次整期的群消息同样 1 小时（手动）/ 一天（自动）最多一条。没配渠道就只发站内通知

**数据权限是自动同步的**：任务里的单位和负责人会变成数据权限——数据集绑定到「填报单位」列，负责人在这个维度（默认「填报单位」）上只能看到、只能填自己负责的单位。同一个维度下的所有任务合并计算，一个人可以在几个任务里各负责几个单位。注意：

- **被指派的负责人会成为「数据范围受限用户」**：导入数据、建视图、定时推送、阈值告警、SQL 保存等会绕过过滤的功能对他们关闭（见上面「数据权限」）。既是负责人又要做分析的人，请改由管理员代填，或接受这个限制
- **没有被指派的用户不受限**，能看到整个数据集（分析汇总的人正需要这样），也能改任何单位的行，和其他数据集一样；管理员代填的单位在看板上显示管理员为提交人
- 这个维度由收集任务管理，**不要在「数据权限」里手动改**：改任务里的单位 / 负责人、删任务时，相关规则会被重新计算或删除
- 把负责人从所有任务里去掉 / 删除任务后，他在这个维度上的规则被删除，回到不受限

任务管理（新建、修改、删除、开启期次）仅管理员；负责人只能看自己的「我的填报」；确认人能看这个任务的看板并审核，但不能改任务、开期次。**确认人不能同时是同一个维度下某个单位的负责人**（负责人只看得到自己的单位，就没法看全部数据来确认），保存时会拒绝。删除任务会删除期次和提交记录，**数据集和已填的数据保留**；已经有人提交的期次不能删除。

目前做到「谁填了、谁没填」、一键生成填报工作簿、退回重填、确认后锁定、截止日期与催办。还没有做按单位不同的审核人 / 多级审核；删除数据集里的行不会撤销该单位的「已提交」状态。

**锁定只管填报入口。** 确认后的单位，通过填报提交 / 删除是被拒绝的；但管理员仍可以在数据集里直接改（导入、编辑行）、撤销某个填报批次，这些操作不经过收集任务的检查，所以不受锁定限制。需要严格防改的话，请把数据集的编辑权限只留给少数管理员。

### 分享链接（只读给没有账号的人）

工作簿的所有者或管理员可以在编辑器里「文件 → 分享链接…」给一个工作簿创建只读链接，发给没有账号的客户、合作方查看（需要开启登录；没开登录时所有人本来就能打开，不需要）。

- **访客能看到什么**：这个工作簿，以及它**用到的数据集**（图表、透视、指标卡、切片器、数据表、公式里写的数据集）。每次打开链接时服务端按工作簿当前内容重新算一遍用到哪些数据集；访问其他数据集、其他工作簿一律拒绝。访客可以点切片器、图表联动、切换页签、滚动，但不能编辑，也不能导出、写 SQL、用 AI、评论、协作、下钻到数据集页面（工作簿里单元格的 SQL / SQLVALUE 公式照常计算，但只能查这个工作簿用到的数据集）。看到的是工作簿**已保存**的最新版本（创建链接前会先保存当前工作簿；以后修改保存后刷新链接就能看到）
- **数据范围跟随创建人**：访客的请求按创建人的数据范围执行，分享出去的数据不会比创建人自己能看到的更多（创建后创建人被限制到某些店铺，访客也只看到这些）。数据范围受限的用户不能创建分享链接
- **链接怎么保管**：令牌 `gls_…` 只在创建时显示一次，库里只存摘要；有效期 7 / 30 / 90 天或永不过期，可备注，一个工作簿最多 20 个；列表里能看到访问次数和最近访问时间。**吊销立即生效**；工作簿进回收站、被彻底删除、创建人账号被停用后链接同样失效（从回收站恢复后又可用）。拿到链接的人都能打开，所以不要把它发到公开的地方，对外发布前建议设有效期
- **边界**：访客身份不是账号，不在用户目录和操作审计的「用户」里，审计里记「打开分享链接」（含工作簿、IP）；分享页的请求会占用与普通用户相同的并发闸门（`LEDGER_HEAVY_QUERIES`）；公式里数据集名来自单元格的写法、`IMPORTRANGE` 这类跨工作簿引用在分享页不可用（显示已保存的结果或报错）
- **访问密码（可选）**：创建链接时可以再设一个 6–128 位的密码。访客打开链接先看到输入框，输对了才能看到工作簿（没输对时连工作簿名称都不透露）；密码另外告诉对方，不放在链接里。库里只存密码的 PBKDF2 摘要；同一条链接连续输错 5 次锁定 10 分钟（失败次数存在数据库里，重启不清零）；审计里记「分享链接密码验证通过 / 失败」。密码不能事后修改：要换就吊销后重建。数据文件结构版本因此升到 4（之后访问令牌限定数据集又升到 5），升级后旧版本程序不能再打开（否则带密码的链接会不输密码就能打开）
- **嵌入到别的网页**：创建链接后对话框里会给出 `<iframe src=".../share/<令牌>?embed=1" …>` 代码（`?embed=1` 隐藏分享页顶栏）。默认**只有本站页面能嵌入它**；要让你自己的网站显示，管理员设置 `LEDGER_EMBED_ORIGINS=https://你的网站`（服务重启生效，写错格式会拒绝启动并说明）。本服务给页面加的响应头：所有页面 `Content-Security-Policy: frame-ancestors 'self'` + `X-Frame-Options: SAMEORIGIN` + `X-Content-Type-Options: nosniff`；分享页另加 `Referrer-Policy: no-referrer`（令牌在网址里，不通过 Referer 泄露给嵌入页或别的网站），配置了嵌入来源后分享页改用 `frame-ancestors <来源…>`（不再带 `X-Frame-Options`）。链接带了访问密码时，访客在嵌入的框架里输入密码。前置 nginx 且由 nginx 提供页面时，上面的头要在 nginx 里加：`add_header Content-Security-Policy "frame-ancestors 'self'" always;`，分享页的 `location /share/` 里改成 `frame-ancestors https://你的网站`
- 反向代理需要放行请求头 `x-share-token` 和 `x-share-proof`，页面路径是 `/share/<令牌>`，输入密码的接口是 `POST /api/ledger/share/unlock`

### 阈值告警

页面「自动化 → 阈值告警」监控一个指标（汇总值，或两个汇总值的比率，如退款额 / 成交额），可以按某一列分组逐组判断（如每家店铺），超过阈值就推送到上面「定时推送」里配置的渠道（企业微信 / 钉钉 / 飞书群、邮件）。渠道、SMTP、出网要求与定时推送相同。

- **只在新出现时通知。** 服务端记录哪些分组正处于「触发中」：新超标通知一次；持续超标默认不重复（可选「每次检查都通知」或「每隔 N 小时再提醒」）；恢复正常后再次超标重新通知。所有渠道都发送失败时不记为已通知，下次检查会重试
- **较上期变化。** 判断依据除了「当前值」，还可以选「较上期变化（百分比 / 绝对值）」，如「销售额较上期下降超过 30%」「退款率较上期上升超过 3 个百分点」。上期是紧挨着本期之前、长度相同的一段（近 7 天对比再往前的 7 天），所以必须设时间窗口（昨天、近 7 天、近 30 天、上月；不支持「本月」）。上期为 0 的分组不算百分比；求和 / 计数类指标本期没有数据按 0 处理，所以「销量掉到 0」的分组也会抓到。最小样本量在比较上期时：求和 / 计数类只看上期够不够，其他指标本期和上期都要够
- **数据停更。** 指标选「数据停更」：看某个日期列最新一条数据距今几天（按店铺等分组就是逐个看谁多久没有新数据），超过设定天数就告警；不能再设时间窗口和最小样本量。某个分组从来没有数据，不会出现在结果里
- **恢复通知（可选）。** 勾选「恢复正常时也通知一下」后，之前通知过的分组不再满足条件时，发一条「已恢复」消息（含持续了多久）。恢复消息没发出去时触发状态保留，下次检查重试
- **样本量保护。** 建议设置「最小样本量」（如订单数不少于 30），样本不足的分组不判断，否则 2 单里退 1 单的店铺会按 50% 触发。没有数据的分组、分母为 0 的分组同样不判断，也不会因此「恢复」
- **时间窗口默认不含今天**（昨天、近 7 天、近 30 天、上月；「本月」到今天为止，月底前不完整）
- **检查时间**：每天 / 每周 / 每月，或某个数据连接同步到新数据后（先重算该连接相关的 SQL 查询，再检查），或某个数据集更新后（默认是告警自己的数据集；选 SQL 查询的结果数据集时，在查询重算写入后检查）；也可以手动「立即检查」。保存前可用「试算」看现在会命中哪些分组，不保存、不发送
- **权限**：告警按服务账号读数据，**数据范围受限的用户不能创建、查看或试算告警**（否则能借告警把范围外的数据推到群里）；告警只有创建人和管理员能修改、删除。修改判断条件（数据集、指标、分组、筛选、窗口、条件）会作废已有的触发状态，之后重新判断
- 评估使用与透视表相同的并发闸门（`LEDGER_HEAVY_QUERIES`），不会挤占交互查询；每条告警保留最近 100 次检查记录

### 事件 Webhook

页面「自动化 → 事件 Webhook」（只有管理员）登记接收地址和订阅的事件。事件发生时服务端把一份 JSON `POST` 到这个地址，用来触发数据管道、在工单系统里建待办、跑自己的脚本。可订阅的事件（共 11 种）：

| 事件 | 什么时候 | `data` 里有什么 |
|---|---|---|
| `dataset.created` | 导入新建、新建填报数据集、新建外部 Parquet 数据集 | `datasetId`、`name`、`source`（import / input / external），导入时还有行数 |
| `dataset.imported` | 向已有数据集追加 / 整体替换 / 按主键更新导入 | `datasetId`、`name`、`mode`、`rowsRead`、`inserted`、`updated`、`replaced`、`skipped` |
| `dataset.deleted` | 数据集移入回收站 | `datasetId`、`name` |
| `dataset.refreshed` | 外部数据集的文件有变化、重新读取了（手动刷新、自动检查、修改读取方式） | `datasetId`、`name`、`trigger`（manual / auto / edit）、`fileCount`、`rows`、新增 / 移除的文件数和列 |
| `sql.refreshed` | SQL 查询重算写入数据集（手动、定时、同步后、数据集更新后），成功或失败 | `queryId`、`name`、`status`、`datasetId`、`rows` 或 `message` |
| `connector.synced` | 数据连接同步结束 | `connectorId`、`name`、`runId`、`trigger`、`status`（success / skipped / failed）、`datasetId`、各项行数、`message` |
| `writeback.submitted` | 填报提交（写入成功） | `datasetId`、`name`、`batchId`、`inserted`、`updated`、`deleted`、`unchanged` |
| `collect.reviewed` | 收集任务审核：确认、退回、撤销确认 | `collectId`、`period`、`units`、`action`、`reason`、`changed` |
| `approval.created` / `approval.decided` | 发起文件审批 / 通过、驳回、撤回 | `approvalId`、`workbookId`、`workbookName`、`status`、发起人、审批人、意见 |
| `alert.triggered` | 阈值告警新触发或按重复策略再次提醒（与渠道通知同时） | `alertId`、`name`、`datasetId`、`hits`（分组、值、`new` / `reminder`） |

- **请求**：`Content-Type: application/json`，请求体 `{ "id", "event", "occurredAt", "actor": { "id", "name" } | null, "data": { … } }`（`actor` 为空表示后台任务触发，如定时同步）。请求头 `X-Gridlake-Event`（事件名）、`X-Gridlake-Delivery`（投递 id，重发时不变，可用来去重）、`X-Gridlake-Signature`
- **只发元信息**（id、名称、行数、操作人），不发数据行，所以不受数据范围限制；需要数据时用访问令牌调接口去取
- **签名**：`X-Gridlake-Signature: t=<秒级时间戳>,v1=<签名>`，签名 = `HMAC-SHA256(密钥, "<t>.<原始请求体>")` 的十六进制。接收方用新建时显示的密钥（`whsec_…`，只显示一次，可「重置密钥」）核对，并拒绝时间戳太旧（如 5 分钟以前）的请求，防重放。对话框里「如何接收」有 Python 示例
- **重试**：对方返回 2xx 算成功；否则（含 10 秒没响应、连不上）在 1 分钟、5 分钟、30 分钟、2 小时、6 小时后重试，共 6 次。事件先写进数据库里的发送队列，服务重启不会丢。**不保证顺序**（按 `occurredAt` 排）；对方处理了但响应超时的，会再收到一次，按 `X-Gridlake-Delivery` 去重
- **发送记录**：每个 Webhook 的最近发送（请求体、对方响应的前 500 个字、状态码、下次重试时间），可以手动重发；保留 7 天、每个 Webhook 最多 500 条。「测试」立即发一个 `ping` 事件并显示结果
- **停用**：排队中的事件不再发送（重新启用后也不补发）；删除时连同发送记录一起删除
- **地址限制**：与网址导入同一套规则——不能是本机、链路本地（含云厂商元数据接口）等地址，连接时和每次重定向都再检查；设置 `LEDGER_URL_BLOCK_PRIVATE=1` 后内网地址也不行。地址和密钥加密存放（与数据连接共用 `secret.key`），列表里地址的查询参数部分打码
- 最多 50 个 Webhook；新建、修改、删除、重置密钥、测试、重发都记审计

### 监控指标与日志

```bash
curl -s -H "x-admin-token: <令牌>" http://服务器:8787/api/admin/metrics     # Prometheus 文本格式
```

访问控制同运维接口（未配置 `LEDGER_ADMIN_TOKEN` 时只允许本机）。Prometheus 抓取示例：

```yaml
scrape_configs:
  - job_name: gridlake
    metrics_path: /api/admin/metrics
    authorization: { credentials: "<LEDGER_ADMIN_TOKEN 的值>" }   # 以 Authorization: Bearer 发送
    static_configs: [{ targets: ["服务器:8787"] }]
```

主要指标：`gridlake_http_requests_total{code="5xx"}`（错误率）、`gridlake_http_request_duration_seconds`（耗时直方图）、
`gridlake_heavy_queries{state="waiting"}`（大计算排队长度，持续大于 0 说明并发不够或有慢查询）、`gridlake_db_size_bytes`、
`gridlake_last_backup_success` / `gridlake_last_backup_age_seconds`（备份是否成功、多久没备份）。建议告警：备份失败或超过 26 小时没有备份、5xx 持续增长、排队长度持续大于 0。

处理时间超过 `LEDGER_SLOW_REQUEST_MS`（默认 3000，`0` 关闭）的请求会在日志里记一条 `慢请求`（方法、路径、状态码、耗时；统计到响应头返回为止，不含查询参数）。
`LEDGER_LOG_FORMAT=json` 让日志每行输出一个 JSON，便于 Loki / ELK 等采集。

`status` / `check` 中的 `problems` 不为空，说明有计算列或关联视图引用的列已不存在（如删除重导了数据集），需要在页面上修改或删除对应的计算列。

### 安装后验收

装好（或升级后）在服务器上执行：

```bash
cd /opt/gridlake && tests/e2e/run.sh
```

它用**安装好的程序**加临时数据库和独立端口（18787 / 19001）跑一遍端到端回归（登录与权限、审批与月结、按店铺的数据范围，约 160 项，十几秒），**不会碰正在运行的服务和数据**。需要服务器有 `python3` 和 `curl`；最后一行是「端到端测试全部通过」才算验收通过，失败的项会列出原因。它验证的是程序在这台机器上的行为，不代表与你们的真实登录网关已经联通——网关要另外用 `curl -H "x-user-token: <令牌>" http://127.0.0.1:8787/api/ledger/me` 检查。

## 六、升级

```bash
tar -xzf gridlake-<新版本>-linux-x86_64.tar.gz && cd gridlake-<新版本>-linux-x86_64
sudo ./install.sh
```

脚本会：停服务 → 用新版程序离线备份当前数据（备份失败则取消升级、恢复原服务）→ 替换程序与页面（保留 `ledger.env` 与 `config/index.js`）→ 启动并做健康检查。数据结构的升级在服务启动时自动完成。

回退：停服务，用升级前的备份 `restore`，再装回旧版本安装包。

### 从 WebExcel 迁移

项目原名 WebExcel，现在叫 Gridlake。旧版本装在 `webexcel` 这个名字下（服务 `webexcel`、用户 `webexcel`、目录 `/opt/webexcel`、`/var/lib/webexcel`、`/etc/webexcel`），新版本的安装脚本发现这种安装会直接停下，不会自动搬数据。迁移步骤（数据文件格式不变，`LEDGER_*` 配置项也不变）：

```bash
# 1. 停旧服务并备份（旧程序的 backup 命令；没有就直接复制整个数据目录）
sudo systemctl disable --now webexcel
sudo cp -a /var/lib/webexcel /var/lib/webexcel.bak

# 2. 改名：用户、目录、配置
sudo usermod -l gridlake webexcel && sudo groupmod -n gridlake webexcel
sudo mv /var/lib/webexcel /var/lib/gridlake && sudo usermod -d /var/lib/gridlake gridlake
sudo mv /etc/webexcel /etc/gridlake && sudo mv /opt/webexcel /opt/gridlake
sudo rm /etc/systemd/system/webexcel.service

# 3. 配置里写了旧路径的地方改成新路径（LEDGER_DB、LEDGER_BACKUP_DIR、收件目录等）
sudo sed -i 's#/webexcel#/gridlake#g' /etc/gridlake/ledger.env

# 4. 解压新安装包，执行 sudo ./install.sh（它会当作升级处理，升级前再备份一次）
```

网页端：升级时保留的 `web/config/index.js` 里如果写着 `window.__webexcel_config`，新页面仍然认（新写法是 `window.__gridlake_config`）。网关登录模式默认读取的令牌 cookie 名仍是 `webexcel-token`（为了不让现有网关失效），要换名字就在 `config/index.js` 里设置 `tokenCookie`。内置账号的会话 cookie 从 `webexcel_session` 改为 `gridlake_session`，升级后所有人需要重新登录一次。

## 七、常见问题

| 现象 | 处理 |
|---|---|
| 启动报「数据文件正被另一个进程使用」 | 已有一个服务在运行（`systemctl status gridlake`），或上次的进程没有退出；同一个数据文件只能被一个进程打开 |
| 大表筛选 / 透视时进程被系统杀掉（OOM） | 不要把 `LEDGER_MEMORY_LIMIT` 调得太大（它不是硬上限，进程内存峰值会超出）：保持默认的 30%，或手动设为服务器内存的 25%~40%；确认 `tmp/spill` 所在磁盘有足够空间；用 systemd `MemoryMax` / Docker `mem_limit` 做兜底，让系统在超限时只重启本服务而不是误杀别的进程 |
| 页面提示「服务器内存不足，这次计算放不下」 | 这次计算超出了内存上限（DuckDB 报 Out of Memory，服务不会崩溃，其他请求照常）。缩小筛选范围、减少汇总维度或排序列后重试；经常出现就调大 `LEDGER_MEMORY_LIMIT` 或给机器加内存 |
| 页面提示「服务繁忙：已有 N 个大计算在进行」 | 大计算排队超过 `LEDGER_HEAVY_WAIT_SECS`。`GET /api/health` 里 `heavy` 能看到上限 / 正在进行 / 排队数，`activeQueries` 长时间不为 0 说明有查询卡着；放弃的查询（关页面、超时）会被自动中断 |
| 内置账号忘记管理员密码 | 另一个管理员在「账号管理」里重置；或停服务后执行 `echo '新密码' \| sudo -u gridlake /opt/gridlake/bin/gridlake reset-password admin --admin`（会读取 `/etc/gridlake/ledger.env` 里的数据库位置；建议直接运行后在提示里输入，避免密码留在 shell 历史） |
| 网关模式登录失败 | 检查 `LEDGER_AUTH_URL` 能否从服务器访问、运行时配置里的 `loginUrl` 与 `tokenCookie` 是否正确 |
| 数据表加载失败、保存状态显示「离线」、公式显示 `#服务不可用` | 表格服务没有响应：`curl http://127.0.0.1:8787/api/health`，查看 `journalctl -u gridlake` |
| 上传大文件失败 | 调大 `LEDGER_MAX_UPLOAD_MB`；前置 nginx 时同时调大 `client_max_body_size` |
| 磁盘占用增长 | 主要是 `backups/`（调小 `LEDGER_BACKUP_KEEP`）与 `tmp/`（可在停服务后清空） |
| 不要做的事 | 不要 `kill -9` 服务进程；不要在服务运行时复制 / 覆盖 `ledger.duckdb`（用备份接口） |
