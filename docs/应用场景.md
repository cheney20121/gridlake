# Gridlake 应用场景：解决什么问题、怎么用

Gridlake 适合这样一类团队：**数据量已经超出 Excel，但业务人员仍然想用 Excel 的方式工作**——随手写公式、拖透视表、自由排版、做成报表发给别人。下面先列出它解决的典型需求，再按业务场景给出具体做法（每个场景都可以用 `bin/gridlake demo` 里的示例数据先试一遍）。

> 下面的场景是典型做法，不是客户案例。具体操作见 [用户手册](用户手册.md)。

---

## 一、它解决哪些需求

| 用户的原话 | 背后的问题 | Gridlake 的解法 |
|---|---|---|
| 「订单表 300 万行，Excel 打不开」 | Excel 上限 104 万行，几十万行就卡 | 数据放在服务端 DuckDB，浏览器只取看到的那一屏；1 亿行打开约 50 毫秒 |
| 「BI 看板改个口径要找 IT 排期」 | BI 擅长固定看板，不擅长临时分析 | Excel 式工作簿：自己写公式、拖透视、排版，透视和公式下推到服务端 |
| 「每个月从系统导出、粘贴、做表，一做两天」 | 重复的手工整理 | 数据连接定时同步 + 模板 + 定时推送，数据更新后报表自动跟着变 |
| 「几十家门店各发一份 Excel，汇总要一个个对」 | 多人填报靠邮件和合并 | 收集任务：大家往同一个数据集里各填各的，看板上看谁没交 |
| 「数据里有重复单、手机号写错、日期乱七八糟」 | 数据质量没人管，发现得太晚 | 数据概况体检 + 校验规则（导入后自动检查）+ 可撤销的数据清洗 |
| 「数字对不上，不知道哪来的」 | 汇总结果没法追溯 | 透视表每个格子双击下钻到明细，自动核对明细合计 |
| 「不同人只能看自己负责的店铺」 | 行级权限 | 按店铺 / 地区 / 部门的数据权限，透视、公式、SQL、导出、AI 统一生效 |
| 「想问一句"上月为什么下降"就有答案」 | 分析门槛 | AI 助手用中文提问，数字都来自查询；会改数据的操作先给建议、确认后才执行 |
| 「报表要发给客户，但不想给他账号」 | 对外交付 | 只读分享链接：可设密码、有效期，数据范围不超过创建人，随时吊销 |
| 「数据不能出公司」 | 合规、私有化 | 开源、单机即可部署，数据都在自己的服务器上；AI 可接自己部署的模型 |

## 二、业务场景

### 场景 1：电商 / 零售经营分析

**谁在用**：电商运营、经营分析、财务 BP。
**痛点**：多店铺、多渠道订单一个月就是几百万行；老板要看日报、周报，临时还要问「为什么这周直播渠道下滑」。

**怎么做**
1. **数据连接**接入订单库（MySQL / ClickHouse）或每天的导出文件，按「主键更新」增量同步。
2. 用内置模板「**月度经营分析**」新建工作簿：切片器选店铺和月份，指标卡显示销售额、订单数、客单价及同比 / 环比，图表看趋势。
3. 临时问题直接在数据表上筛选、加**分类汇总**（按渠道看小计），或拖一个**透视表**：渠道 × 月份，值显示「环比」。
4. 问 **AI 助手**：「本周直播渠道比上周少了多少，主要是哪些店铺？」——两期对比归因，结论里的数字可追溯。
5. **定时推送**每天 9 点把经营日报发到企业微信群；**阈值告警**在退款率超过 5%、或某店铺 2 天没有新订单时通知。

**用到的功能**：数据连接、模板、仪表盘（切片器 / 指标卡 / 图表）、透视表、分类汇总、AI 助手、定时推送、阈值告警。
**效果**：报表从「每天手工做」变成「数据到了自动更新」；临时分析不用等 IT，几百万行也能当场拖出来。

### 场景 2：财务对账与月结

**谁在用**：会计、出纳、财务共享中心。
**痛点**：银行流水、平台资金流水、ERP 应收应付要逐笔勾对；月底要锁账，改过的数要留痕。

**怎么做**
1. 导入银行流水和企业账，用模板「**银行余额调节表**」或「**应收应付对账**」：按金额 + 日期窗口自动勾对，列出未达账项，调整后余额自动核对。
2. 对账结果是一个数据集，可以筛出未勾对的记录、导出给业务方确认。
3. 透视表核对科目余额，任一格子**下钻**到明细并自动核对合计。
4. 电商企业可以开启**电商资金台账场景包**：导入抖店资金流水、店铺档案、余额勾稽、月结锁账与审批。
5. 关键工作簿走**文件审批**；所有改动有**版本历史**和**操作审计**。

**用到的功能**：对账模板、下钻核对、文件审批、版本历史、操作审计、场景包（可选）。
**效果**：几十万笔流水的勾对在服务端完成，结果可追溯、可审计。

### 场景 3：连锁门店 / 多部门数据收集

**谁在用**：区域运营、集团财务、HR、行政。
**痛点**：每月让 50 家门店填经营数据，Excel 发出去、收回来、合并、催交，版本混乱。

**怎么做**
1. 建一个数据集（门店、月份、营收、成本、客流…），在**收集任务**里设好单位列（门店）、期次列（月份），添加门店并指定负责人。
2. 每月「开启新一期」、设截止日期；店长在「**我的填报**」里只看到自己的门店，可以批量粘贴。
3. 区域经理在看板上看谁填了、谁没填，一键「催办」推送到群，审核后「确认」或「退回」。
4. 收上来的数据直接是一个数据集：透视、仪表盘、告警都能用；**数据权限**保证每个人只看到自己负责的门店。

**用到的功能**：收集任务、我的填报、数据权限（行级）、催办推送、透视表、仪表盘。
**效果**：收集、催交、审核、汇总在一个地方完成，不再合并几十个 Excel。

### 场景 4：供应链与库存

**谁在用**：计划、采购、仓储。
**痛点**：出入库流水量大，要按商品算期初、入库、出库、期末；断货和异常要早发现。

**怎么做**
1. 导入或同步出入库流水，用模板「**库存进销存**」：按月算期初 + 入库 − 出库 = 期末；透视表里用**计算项**「期末库存」。
2. **窗口计算**：每个商品按日期算累计出库、7 日移动平均销量，生成新数据集（流水更新后自动重算）。
3. **阈值告警**：某商品期末库存低于安全库存、或某仓库数据停更时通知。

**用到的功能**：模板、透视表计算项、窗口计算、阈值告警、数据连接。

### 场景 5：数据质量治理

**谁在用**：数据管理员、业务系统负责人、数据分析师。
**痛点**：上游数据有重复单、手机号格式不对、必填字段为空、取值不规范（「北京」「北京市」）；问题在报表里才暴露。

**怎么做**
1. 拿到新数据先看**数据概况**：每列的空值、不同值个数、范围、认不出的日期，一眼看到问题列。
2. 给关键列设**数据校验规则**：订单号不能重复、手机号符合格式、金额在合理范围、状态只能是规定的几个值。之后**每次导入、同步后自动检查**，数据表上方显示「校验：N 项不通过」。
3. 点「只看这些行」筛出不合格的数据，导出给上游修正；或用**数据清洗**处理：去重、去空白、统一写法、补空值、删除不合格的行——都先看改前改后，最近一次可撤销。
4. 用**拆分列**把「省-市-区」拆开、用**计算列**统一口径，这些都不改原始数据，新数据自动适用。
5. 订阅 `dataset.validation_failed` **Webhook**，校验失败时自动开工单或通知负责人。
6. 也可以直接让 **AI 助手**体检并给出清洗建议。

**用到的功能**：数据概况、数据校验、数据清洗、拆分 / 合并列、计算列、Webhook、AI 助手。
**效果**：问题在数据进来时就被发现，处理过程可预览、可撤销、有审计。

### 场景 6：数据团队的自助分析平台

**谁在用**：数据分析师、数据工程师。
**痛点**：业务方要数，分析师写 SQL 导出 Excel，Excel 又打不开；数仓里的 Parquet 文件业务看不了。

**怎么做**
1. 数据湖 / 对象存储里的 Parquet 建成**外部数据集**：不复制，业务直接浏览、筛选、透视；设置自动检查，新分区到了自动刷新。
2. 分析师在 **SQL 工作台**里写好口径（只读、参数化），**另存为数据集**并设成「源数据更新后」重算，业务在上面自由分析。
3. 排名、累计、同比这类逐行计算用**窗口计算**，不用写窗口函数。
4. 用 **MCP** 让 Claude Desktop、Cursor 等外部 AI 只读查询授权的数据集；用**个人访问令牌**和 REST 接口（[OpenAPI](openapi.json)）接入自己的脚本。

**用到的功能**：外部数据集、SQL 工作台、窗口计算、MCP、访问令牌、REST API、Webhook。

---

### 场景 7：给客户、合作方交付报表

**谁在用**：服务商、代运营公司、品牌方对接经销商。
**痛点**：报表要给外部看，不想开账号，又怕给多了数据。

**怎么做**
1. 做好一个仪表盘工作簿（切片器 + 指标卡 + 图表）。
2. 生成**只读分享链接**：设访问密码和有效期；对方看到的是实时数据，能点切片器，不能编辑、不能导出；数据范围不超过创建人。
3. 或者用**定时推送**每周把报表发到对方邮箱；不需要了随时吊销链接。

---

### 场景 8：个人分析师处理本机大文件

**谁在用**：任何手里有大 CSV / Parquet、又不想装数据库的人。

**怎么做**
```bash
bin/gridlake open 订单.parquet 客户.csv
```
浏览器自动打开：筛选、排序、透视、写公式、做图表，数据在本机，不需要登录、不需要服务器。

## 三、不太适合的场景（诚实说明）

| 场景 | 原因 | 建议 |
|---|---|---|
| 业务系统的在线交易库（每秒大量写入） | DuckDB 是分析型引擎，单机、单写 | 业务系统照常用 MySQL / PG，Gridlake 定时同步过来分析 |
| 十亿行以上、需要集群扩展 | 目前是单机 DuckDB，没有分布式 | 先在数仓里聚合，再把结果给 Gridlake |
| 秒级实时大屏 | 数据连接按计划同步，不是流式 | 用流处理 + 专门的实时大屏 |
| 每列严格类型、一行一条记录的轻量应用（CRM、工单） | Gridlake 是 Excel 式自由表格 | Airtable / NocoDB / Teable 一类更合适 |
| 需要完整 Excel 宏（VBA） | 不支持 VBA | 用公式、模板、SQL、Webhook 替代 |
